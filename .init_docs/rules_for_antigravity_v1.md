

# 📋 МАСТЕР-ДОКУМЕНТ: Сборка универсальных правил

**Для агента:** Gemini (Antigravity v2.18.1)
**Задача:** Собрать переносимый свод правил для Python + JS + HTML + CSS проектов **во временной папке**, не трогая рабочий проект и не привязываясь к конкретному репозиторию.
**Принцип:** сначала staging → ручная проверка → потом перенос в проект.

---

## 0. КРИТИЧЕСКИЕ ЗАПРЕТЫ

**До явной команды «переносим в проект» — ЗАПРЕЩЕНО:**

- ❌ Создавать/менять `.agents/rules/*` в корне любого проекта
- ❌ Создавать/менять `AGENTS.md` / `GEMINI.md` в корне проекта
- ❌ Создавать/менять `.agents/hooks.json` в проекте
- ❌ Менять `~/.gemini/GEMINI.md`, `~/.gemini/AGENTS.md`, `~/.gemini/config/*`
- ❌ Запускать `npx github:KeithTorda/gravirules init` в корне проекта
- ❌ Запускать `codebase-memory-mcp install`
- ❌ Устанавливать что-либо глобально

**Всё делаем только в:**
```
<project>/scratch/rules-staging/
```

Папка `scratch/` — в `.gitignore`. Проверь **до** начала. Если нет — добавь.

## 1. КОНТЕКСТ

Правила должны быть **универсальными** под любой проект пользователя:
- **Языки:** Python 3.11+, JavaScript (ES-модули), HTML5, CSS3.
- **Стек-агностично:** никаких упоминаний конкретных фреймворков, библиотек, доменов.
- **Переносимо:** копируется из проекта в проект без правок.
- **Применимо:** работает и для пет-проекта, и для крупного репо.

**Что НЕ должно быть в правилах:**
- Имена конкретных файлов/классов (`SailRig`, `WinchModel`)
- Имена доменов (физика, финансы, медицина)
- Имена проектов (SIA, MyApp)
- Ссылки на конкретные фазы рефакторинга (`P0a`, `Closes: P1b`)

**Что должно быть:**
- Общие архитектурные принципы
- Языковые правила
- Правила коммитов и тестов
- Инварианты, применимые к любому коду

### 5.2. `00-research-protocol.md` (always_on)

Перед ЛЮБЫМ изменением кода — построить карту зависимостей. Приоритет: **граф → grep → offline**.

**Проверка доступности графа:**
```bash
codebase-memory-mcp cli search_graph '{"name_pattern": ".*", "limit": 1}'
```

- Вернул данные → используй граф.
- Пусто/ошибка → fallback на grep (degraded mode, зафиксируй в отчёте).

**Через граф:**
1. `search_graph(name_pattern="<имя>")` — поиск символа.
2. `trace_path(function_name="<символ>", direction="inbound", depth=3)` — кто вызывает.
3. `trace_path(function_name="<символ>", direction="outbound", depth=3)` — что вызывает.
4. `get_code_snippet(symbol="<имя>")` — точный код.

**Blast radius:**
- Inbound > 10 → breaking, остановись.
- Outbound > 5 → хаб, резать нельзя без плана.
- Циклы → зафиксируй, не исправляй «заодно».

**Через grep (если граф недоступен):**
- Узкий паттерн, не «на всякий случай».
- Файл > 400 строк — читай секциями.
- В отчёте: «degraded mode».

**После изменения:** повтори `trace_path` inbound, убедись, что вызывающие не сломаны.

### 5.3. `01-architecture.md` (always_on)

**Размер и структура:**
- Файл > 400 строк — сигнал к декомпозиции.
- Функция > 50 строк — режь. Метод > 80 — режь. `__init__` > 30 — фабрика.
- Один модуль — одна ответственность. Если не можешь назвать одним существительным без «and» — режь.

**Пакеты и импорты:**
- `__init__.py` / `index.js` — только реэкспорт. Никакой логики, никаких eager-импортов.
- Листовые узлы (общие типы, схемы, утилиты) — в отдельном `contracts/` / `shared/` / `lib/`.
- Импорты только вниз по стеку. Обратные — запрещены. Циклы — баг.
- Никаких `import *`.

**Данные и код:**
- Данные ≠ код. Литералы > 50 строк — в YAML/JSON.
- Конфиги — в отдельных файлах, не в коде.

**Публичный API:**
- Стабилен. Меняешь сигнатуру — сначала найди всех потребителей, обнови в одном коммите.

**Константы:**
- Все человекоуправляемые параметры — в шапке модуля с описанием.
- Магические числа запрещены (кроме `0`, `1`, `-1`, `2`, `100%`).
- Единицы измерения — в имени (`TIMEOUT_S`, `MAX_SPEED_KT`).

### 5.4. `02-no-crutches.md` (always_on)

Следующие паттерны — автоматический отказ. Если задача требует любого из них — остановись и сообщи.

- `window.X = ...` в новом JS — только `export`.
- `try: ... except Exception: pass` — запрещено.
- Хардкод данных > 20 строк — только в YAML/JSON.
- `if not isinstance(...)` для валидации — только через схемы (Pydantic, zod, др.).
- Дублирование блока > 5 строк между файлами — выноси в общий модуль.
- Импорт из `__init__.py`/`index.js` внутри пакета — запрещён.
- `# type: ignore` без причины — запрещён.
- `TODO` без автора и даты — запрещён.
- Магическое число в теле функции — только константа.
- Константа без описания — запрещена.
- Закомментированный код — удаляй, git помнит.

**Если задача не решается без костыля — сообщи:**
> «Задача требует структурного изменения в `<модуль>`. Костыль нарушит правило `<номер>`. Предлагаю сначала рефакторинг.»

### 5.5. `03-python.md` (glob `*.py`)

- **Типизация:** обязательна. Все параметры и возвраты. `from __future__ import annotations`.
- **Валидация:** Pydantic (или аналог) на границах системы. Не `if not isinstance(...)`.
- **Логирование:** `logging.getLogger(__name__)`. Никаких `print()`.
- **Исключения:** только конкретные. Никаких `except Exception: pass`. Логируй с контекстом.
- **Дефолты:** никаких мутабельных (`def f(x=[])`). Только `None` + инициализация.
- **Docstring:** для публичных функций и классов. Summary, пустая строка, аргументы если неочевидны.
- **Импорты:** абсолютные. Не `from .x import ...`.
- **Форматирование:** f-strings. Никаких `%` или `.format()`.
- **Константы:** в шапке модуля. `Final[type]`. С описанием. Единицы в имени.
- **Стиль:** ruff / black / isort по конфигу проекта. Если конфига нет — дефолты.

---

### 5.6. `04-javascript.md` (glob `*.js`)

- **Модули:** ES-модули (`import`/`export`). Никаких `window.X = ...`.
- **Переменные:** `const` по умолчанию, `let` только если реально меняется. `var` запрещён.
- **Сравнения:** `===`/`!==`. Никогда `==`/`!=`.
- **Асинхронность:** `async/await`. Промисы без `await` — только fire-and-forget с `.catch(...)`.
- **Функции:** > 40 строк — режь. `handle*` > 80 — это не handler, это сервис.
- **HTML в JS:** через `<template>` в HTML. `innerHTML = '<большой кусок>'` запрещён. Мелкие (1–2 тега) — можно.
- **Константы:** `SCREAMING_SNAKE_CASE`. `Object.freeze()` для конфигов. JSDoc с единицами.
- **DOM:** кэшируй запросы. `getElementById` в цикле или в `requestAnimationFrame` запрещён.
- **JSDoc:** для публичных функций — summary + типы аргументов.
- **Стиль:** eslint / prettier по конфигу проекта. Если нет — дефолты.

---

### 5.7. `05-html.md` (glob `*.html`)

- **Семантика:** `<header>`, `<nav>`, `<main>`, `<section>`, `<footer>`. `<div>` — только когда ничего не подходит.
- **`id` vs `class`:** `id` — для JS-хуков. `class` — для стилей. Не смешивать.
- **Данные:** `data-*` атрибуты для параметров. Не прячь в `id` или `class`.
- **Инлайн-стили:** запрещены (кроме динамических через JS `style.transform`).
- **Инлайн-скрипты:** запрещены. Только `<script src>` или `<script type="module">`.
- **Повторы:** модалки, тултипы, шаблоны — в `<template>`. Один раз в HTML.
- **Секции:** > 100 строк — разбей комментарием-заголовком (`<!-- === SECTION === -->`).
- **Атрибуты:** порядок — `id`, `class`, `data-*`, `type`/`name`, `aria-*`, `role`. Кавычки двойные.
- **Доступность:** `aria-label` на иконочных кнопках, `role` на кастомных виджетах, `alt` на `<img>`.
- **Вёрстка:** никаких `<br>` для отступов. Только CSS.

### 5.8. `06-css.md` (glob `*.css`) — новый файл

- **Переменные:** цвета, отступы, шрифты — в `:root` через CSS-переменные. Никаких магических значений в правилах.
- **Единицы:** `rem` для шрифтов и отступов, `px` только для бордеров и тонких линий. Избегай `em` кроме специфичных случаев.
- **Селекторы:** максимум 3 уровня вложенности. `.a .b .c .d` — режь.
- **`!important`:** запрещён кроме override сторонних библиотек. Если используешь — комментарий с причиной.
- **Дублирование:** блок правил > 5 строк, встречающийся 2+ раз — выноси в класс-утилиту.
- **Карточки, панели, кнопки:** общий базовый класс (`.card`, `.btn`, `.panel`) + модификаторы. Не копипастить `bg + border + radius + padding` в 30 селекторов.
- **Свечения и тени:** утилиты (`.glow-*`, `.shadow-*`). Не хардкодить `box-shadow` в каждом правиле.
- **Скроллбары:** один общий класс, а не 4 копии.
- **Медиа-запросы:** группируй в конце файла или в отдельном файле. Не разбрасывай по всему CSS.
- **Комментарии-разделители:** `/* === SECTION NAME === */` для логических блоков.
- **Файл > 1000 строк:** сигнал к разбивке на модули (`layout.css`, `components.css`, `zones/*.css`).
- **Вложенность через `@layer`:** если проект поддерживает — используй для каскада. Если нет — плоский CSS с БЭМ-подобными именами.

### 5.9. `07-tests.md` (glob `test_*`, `*_test.*`)

- **Один тест — одна проверка.** Имя: `test_<что>_<условие>_<ожидание>`.
- **Структура:** Arrange / Act / Assert. Пустая строка между блоками.
- **Фикстуры:** в `conftest.py` / `setup.js`. Не дублируй создание объектов.
- **Моки:** только на границах (HTTP, файлы, время, RNG). Не мокай внутренние функции.
- **Изоляция:** тест не ходит в сеть/диск, кроме `tmp_path`.
- **Время:** никаких `time.sleep()`. Для асинхронности — `freeze_time` / моки таймера.
- **Параметризация:** `@pytest.mark.parametrize` (или `test.each`) для однотипных кейсов.
- **Багфикс:** упал баг → сначала тест, потом фикс.
- **Границы:** валидный + минимальный + максимальный + невалидный + None. Всегда.
- **Порядок:** тесты не зависят от порядка выполнения. Каждый — изолирован.
- **Покрытие:** не гонись за 100%. Фокус на границах и бизнес-логике.

### 5.10. `08-commits.md` (model_decision)

**Когда делать коммит:**
- Один коммит = одно логическое изменение. Не «фича + багфикс» в одном.
- Коммит после каждого зелёного прогона тестов.
- Не коммить сломанное. Кроме WIP-ветки (`wip/`, не `main`).
- Рефакторинг — отдельно от фич.
- Перед коммитом: `git diff --staged` — прочитай глазами.
- Не коммить: `.env`, `__pycache__/`, `node_modules/`, `*.log`, `scratch/`, локальные IDE-конфиги.

**Как писать:**
- Формат: `<тип>(<область>): <описание>`.
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`.
- Описание: императив, строчная, без точки.
- Первая строка ≤ 72 символов. Длиннее — в тело.
- Тело: **зачем**, а не что. «Что» видно в diff.
- Breaking change: восклицательный знак после типа (`refactor(api)!:`).
- Один язык в репозитории. Если существующие коммиты на русском — новые тоже.
- Не писать: «исправил», «обновил», «WIP», «fixes», «minor changes».

**Примеры:**
```
refactor(api): вынести валидацию в Pydantic-схемы

58 строк ручных проверок дублировали модели. Заменил на
DTO с автоматической валидацией и 422 вместо 500.

Closes: #123
```

```
fix(auth): не логировать токен при ошибке

Токен попадал в traceback при невалидном запросе.
Убрал из контекста логирования.
```

## 7. ВАЛИДАЦИЯ (`validation/`)

### 7.1. `check-size.sh`

```bash
#!/usr/bin/env bash
for f in draft/*.md; do
  size=$(wc -c < "$f")
  if [ "$size" -gt 12000 ]; then
    echo "❌ $f: $size (> 12000)"
  else
    echo "✅ $f: $size"
  fi
done
```

### 7.2. `check-frontmatter.sh`

```bash
#!/usr/bin/env bash
for f in draft/*.md; do
  if head -1 "$f" | grep -q "^---$"; then
    trigger=$(sed -n '2,10p' "$f" | grep "^trigger:" | head -1)
    if [ -n "$trigger" ]; then
      echo "✅ $f: $trigger"
    else
      echo "❌ $f: нет trigger"
    fi
  else
    echo "❌ $f: нет frontmatter"
  fi
done
```

### 7.3. `report.md`

Содержит:
- Список файлов с размерами.
- Список триггеров.
- Источники, откуда взято.
- Что не влезло / требует доработки.
- Открытые вопросы.

## 10. ПЕРЕНОС В ПРОЕКТ (только после команды)

**Не переносить без явного «Проверил, переносим».**

После команды:
1. Скопировать `draft/*.md` → `.agents/rules/`.
2. Скопировать `hooks/hooks.json` → `.agents/hooks.json`.
3. Скопировать `hooks/graph-router.sh` → `scripts/graph-router.sh`, `chmod +x`.
4. Проверить MCP-конфиг (путь зависит от проекта).
5. Запустить тесты.
6. Открыть приложение/UI.
7. `/memory show` — проверить, что правила в контексте.

**До этой команды — проект не трогаем.**

## 12. ПРОВЕРКА УНИВЕРСАЛЬНОСТИ

Перед сдачей staging — прогони мысленный тест:

1. Возьми любой свой проект — Python CLI, JS-виджет, статичный HTML-сайт.
2. Открой каждый файл правил.
3. Задай вопрос: **«Применимо ли это к проекту, где нет `physics/`, нет `workbench/`, нет SIA?»**
4. Если в правиле упоминается что-то конкретное из SIA — перепиши обобщённо.

**Пример:**
- ❌ «Файлы физики > 400 строк — режь»
- ✅ «Любой файл > 400 строк — сигнал к декомпозиции»

- ❌ «`SailRig` не должен импортировать `physics.forces`»
- ✅ «Модули не должны создавать циклических импортов»
